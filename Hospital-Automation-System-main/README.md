# Hospital-Automation-System

## Local setup

```bash
python -m venv venv
```

On Windows:

```powershell
venv\Scripts\activate
```

Install backend dependencies:

```bash
pip install -r requirements.txt
```

Create your local environment file from the sample:

```bash
copy .env.example .env
```

Then run the backend tests:

```bash
pytest
```

For the frontend in the React app:

```bash
cd frontend-react
npm install
npm run dev
```

The app supports demo mode out of the box. Leave `DEMO_MODE=true` and `ATTENDANCE_MODE=demo` for local hospital automation demos without external attendance devices or Gemini credentials. PostgreSQL may also be configured with `DATABASE_URL` or the `POSTGRES_*` variables.

## Demo deployment: Vercel frontend and Render API

The root `vercel.json` builds and serves the React frontend. Import this
repository into Vercel with the repository root as the project root. The
included configuration sets the install command, build command, output
directory, and single-page-app route fallback.

The root `render.yaml` describes a demo FastAPI web service and a demo
PostgreSQL database. Connect the same GitHub repository to Render as a Blueprint
and provide these private environment values when prompted:

- `INITIAL_ADMIN_PASSWORD`: a unique password of at least 12 characters for
  the initial admin account.
- `CORS_ALLOWED_ORIGINS`: the Vercel site's exact origin, such as
  `https://your-project.vercel.app`.

After Render deploys, set `VITE_API_BASE_URL` in Vercel to the Render API base
URL (without a trailing slash) and redeploy the frontend. Keep `JWT_SECRET_KEY`
generated by Render. Change the admin password after the first login.

This is a demo configuration, not a production deployment. Render's free web
service sleeps after inactivity, so background automation is paused until the
next request wakes the API. Its free PostgreSQL database expires after 30 days,
has no backups, and has a 1 GB limit. Uploaded files use the service's
ephemeral filesystem and can be lost on restart or redeploy. Do not use this
setup for real hospital operations or sensitive data; use persistent paid
compute and storage with backups for production.

## Import nursing shift logs

The nursing shift-log response workbook can be imported by an administrator through
`POST /nursing-shift-logs/import` as a multipart `.xlsx` file. The importer expects
the form-response columns `Timestamp`, `1. Nurse Name`, `2. Date`, `3. Shift`,
and `4. Ward / Area`; it preserves the other answer columns in each stored record.
Imports are limited to 500 rows and 5 MB. Re-uploading identical rows skips them,
so the same workbook can be safely imported again.

Importing a shift log stores historical report data; it does not create entries
in the staff roster. Roster shifts are configured separately in **Shifts** and
assigned in the **Staff Automation** scheduler. A roster can contain multiple
different shifts for one employee on the same date. In the scheduler, select a
shift brush and click a date cell to add or remove that shift; **Off / Clear**
removes all shifts for that employee/date.

Open the backend's `/docs` page, authorize as an administrator, select
`POST /nursing-shift-logs/import`, and upload the workbook. Imported records can
be checked with `GET /nursing-shift-logs/`, optionally filtered by `nurse_name`
or `shift_date`.

## Staff Automation data sources

The React Staff Automation page uses authenticated backend APIs for employees,
today's and active overnight rosters and check-ins, task templates, work-queue items, assignments,
agent actions, workflow traces, approvals, and shift reports. It does not seed
staff or live activity records. On startup, the backend idempotently seeds a
role-specific library of 34 recurring operational templates and their daily
schedules across Nursing, Ward, Pharmacy, Laboratory, Reception, and
Housekeeping. Historical shift-report statistics are
returned by `GET /nursing-shift-logs/analytics` and are labeled separately from
live operations.

In non-production environments, startup also seeds 56 clearly named `Demo`
employees across the six task-library departments, three demo shifts per
department, and scheduled rosters for the current day and following six days.
Their roles and skills match the seeded task templates, so supervisors can exercise the actual check-in,
task-generation, assignment, and status flows. The seed is idempotent and does
not create fake check-ins, tasks, assignments, agent logs, or workflow traces;
those are created only when the real application workflows run. It is enabled
by default outside production and can be disabled with
`DEMO_DATA_ENABLED=false`. Production always skips the demo staff seed.

Staff check-in is accepted only when a matching current or upcoming roster
exists; task eligibility also requires an active rostered shift and a current
check-in. Overnight shifts use the roster's work date and the shift's database
times. Check-in and check-out both use the Event Agent and Orchestrator.
Check-in materializes the active recurring task templates for the checked-in
employee's department and shift (currently five to eight tasks per department),
then runs the assignment cycle across qualified employees who are actually
checked in. Repeated check-ins do not duplicate same-day task work. Normal
scheduler runs create work only for a matching active roster; when no eligible
employee is checked in, generated work remains pending and assignment events
are withheld. A later check-in or shift-start event reevaluates pending work.
The absentee watcher marks a scheduled worker absent after the configured
check-in grace period and automatically reassigns their unstarted tasks to
checked-in, active staff who match the task's department, shift, and skill
requirements; assignment selection also considers current workload. A late
worker becomes eligible for new assignments once checked in. Staff-shortage
events retry automatic assignment before escalating. Overdue unstarted tasks
are automatically reassigned using the same eligibility rules. In-progress
tasks are not interrupted by timeout recovery, and work remains pending with a
supervisor escalation when no qualified replacement is available.
An unfinished work item for the same task, department, and shift suppresses
duplicate generation until that item is completed or cancelled.
Production check-in/check-out events must come from the registered attendance
device API. The Staff Automation page's explicitly labeled **Manual override**
controls are for demo/testing and publish the same `WORKER_CHECKED_IN` and
`WORKER_CHECKED_OUT` events through the Event Agent and Hospital Orchestrator.
Attendance events are persisted with their source and linked agent action logs.
The attendance page refreshes live roster, check-in source, work duration, and
workload data. The attendance view links to the Shift Scheduler for creating or
changing a roster.

The Staff Automation page also includes a **Monthly Attendance** tab. It defaults
to the current month and shows each employee's daily attendance code alongside
recorded check-in and check-out times. Use the department dropdown to narrow the
staff list. Shifts are tracked separately, and a future shift stays blank until
its scheduled start. The legend is **P** (present: early or within 30 minutes of
shift start), **L** (late: over 30 minutes and through 2 hours after start),
**Z** (half-day: over 2 hours after start), **A** (absent: no check-in by the
2-hour cutoff or after a missed shift ends), and **H** (a date in the supplied
2026 Maharashtra holiday calendar). Non-holiday dates without a roster remain
blank. The adjacent **Holiday Count** tab lists all 24 holidays from the
provided Maharashtra list, including bank-only and state/local dates, and
counts each staff member once per holiday date with a recorded check-in.
Times are displayed in the viewer's local time.

The page submits staff check-in/check-out and emergency/task-completion events
through the existing backend event gateway, runs due recurring work through
`POST /scheduler/run`, and submits reports through `POST /nursing-shift-logs/`.
Task templates use the existing Task Master API and recurring schedule system.
Seeded templates include a required role and skill, priority, estimated
duration, suggested start/due times, proof requirement, and active state. Their
daily schedules create work through the Task Management Agent when a matching
rostered shift is active. Obsolete sample templates are deactivated and their
open work is cancelled; completed work and assignments are retained. Templates
may require verified proof; completion is blocked until the Task Verification
workflow verifies a submitted proof. Custom templates may leave proof optional.
Templates may also specify a required role and skill; the
Workforce Agent filters available checked-in staff against those requirements
and escalates when no qualified employee is available.

The Staff Automation view also presents actual pending workflow approvals,
orchestrator traces, agent actions, and transactional outbox status (including
Communication Agent notifications). Its Historical Insights section can analyze shift reports
for recurring operational signals, persist recommendations, configure follow-up
rules from existing task templates, and review rule execution/effectiveness
history. Analysis is descriptive: it requires at least 10 valid observations,
3 occurrences, and a 10% recurrence rate. Recommendations and configured rules
start pending; an active supervisor/admin account linked to an employee record
must explicitly approve a rule before it can run. Only approved rules can
create supervisor task requests, which continue through the existing
supervisor-request outbox, orchestrator, Task Management Agent, and Assignment
Agent. Rules cannot make clinical decisions, select clinical protocols, or
assign staff themselves.

The learned-rule API is rooted at `/staff-automation`:

- `POST /pattern-learning/analyze` analyzes retained shift reports and
  upserts pending recommendations.
- `GET /recommendations` and `GET /rules` list persisted records.
- `POST /recommendations/{id}/rules` creates a rule pending approval;
  `PUT /rules/{id}` edits a pending rule.
- `POST /rules/{id}/approve`, `/reject`, and `/disable` record lifecycle
  decisions; `POST /rules/expire` marks due rules expired; `GET /audit`
  provides the append-only transition history.
- `GET /rules/{id}/executions` and `/effectiveness` report idempotent trigger
  results, failures, and whether the existing supervisor-request workflow has
  processed each generated request. A successful dispatch means the request
  was queued; it does not claim that downstream work was completed.

Rule and audit tables are additive and created through the existing SQLAlchemy
metadata initialization; existing historical shift-report rows are retained.

## Attendance devices and image proof verification

An external attendance device can use the vendor-neutral endpoint
`POST /device-attendance/event`. An administrator first enrolls its ID for an
employee with `POST /admin/attendance-devices/`; the response returns a
one-time device token. Store that token on the device and send it as
`X-Device-Token`. The event body is:

```json
{
  "device_id": "FRONT-DESK-01",
  "employee_id": 123,
  "event": "CHECK_IN",
  "occurred_at": "2026-10-21T08:00:00+05:30"
}
```

Set `event` to `CHECK_IN` or `CHECK_OUT`. The backend rejects unknown/revoked
devices, employee/device mismatches, duplicate check-ins, and stale check-in
timestamps. Both device events enter the same internal attendance event
workflow: Workforce Agent, scheduled task generation, Assignment Agent, and
the Communication Agent's outbox notification path. Check-out follows the
existing shift-handover policy. This is an API contract for an external device;
it does not claim integration with a specific hardware vendor. The general
`/events` attendance route only accepts events explicitly marked
`trigger_source=MANUAL_OVERRIDE`; production device events use the authenticated
device endpoint.

Uploaded or WhatsApp-submitted proof images are evaluated with Gemini when
`GEMINI_API_KEY` is configured. `GEMINI_VISION_MODEL` defaults to
`gemini-2.5-flash`. The model receives the task name, task description, and
image, and returns a decision, confidence, and rationale. The configured
`MIN_VERIFICATION_CONFIDENCE_SCORE` is the shared confidence threshold.
The verification workflow returns `APPROVED`, `REJECTED`, or `NEEDS_REVIEW`;
unclear, unavailable, or below-threshold AI results are routed to human review.
Automated completion remains opt-in through
`ENABLE_AUTOMATED_PROOF_APPROVAL`; it defaults to `false`, so a verified
image still waits for supervisor approval. Rejected proof leaves the task
incomplete and requests resubmission. Missing credentials, provider errors,
invalid model output, and low-confidence results are routed to supervisor
review rather than being treated as successful verification.

WhatsApp continues to use mock delivery by default (`WHATSAPP_MOCK=true`) and
stays mocked if the access token or phone-number ID is missing, even if mock
mode is disabled. Live delivery requires the Meta Cloud API credentials to be
provided only through `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, and
`WHATSAPP_APP_SECRET` environment variables, with `WHATSAPP_MOCK=false`.

At startup, the backend registers the eight fixed agent IDs used by existing
action logs. The admin **Agents** page then lists the registered agents and
their capabilities, statistics, and action history.
